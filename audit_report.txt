1. SECURITY — SECRETS & REPOSITORY HYGIENE   [HIGH / MEDIUM / LOW]
--------------------------------------------------------------------------------
1.1 [HIGH] .gitignore is far too permissive
     - File: .gitignore (root) = only ".idea / node_modules / *.log".
     - Finding: .env, .env.*, *.key, .modelweaver/, __pycache__/, *.db,
       *.sqlite* are NOT ignored (verified by reading the file). This is what
       allowed issue 1.2 and permits accidental future commits of secrets and
       databases.
     - Recommendation: add at least:
           .env
           .env.*
           *.key
           .modelweaver/
           __pycache__/
           *.db

1.2 [MEDIUM] Tracked ".env"-style file (.env.committed) — hygiene / misleading
     - File: .env.committed (root, tracked in git).
     - CORRECTION vs. earlier reports: the file body contains NO actual API
       keys. It is a warning placeholder whose header reads
       "Clés API commitées dans .env — À révoquer AVANT la V2" and lists the
       providers openrouter / groq / opencode-zen. No live secret value was
       found anywhere in the working tree (grep for sk-/gsk-/AIza… patterns
       returned only legitimate code identifiers, never key literals).
     - Risk: the *pattern* of committing a dotenv file to git history is
       dangerous (it normalises secret-in-repo behaviour and, if real keys are
       ever added, they land in history permanently). Severity is therefore
       MEDIUM (hygiene / foot-gun), not CRITICAL — there is no confirmed leak.
     - Recommendation: move the warning into a non-dotenv tracked doc
       (e.g. SECRETS_POLICY.md) and stop versioning any file named ".env*".

2. DOCKER HARDENING   [HIGH / MEDIUM]
--------------------------------------------------------------------------------
2.1 [HIGH] Container runs with maximal privileges (sandbox effectively disabled)
     - File: docker-compose.yml (verified).
     - Finding: cap_add SYS_ADMIN + SYS_PTRACE and
       security_opt seccomp=unconfined, combined with the ${PWD}:/app bind
       mount of the whole repo and /dev/dri passthrough. This defeats
       container isolation and allows privilege escalation / host escape.
     - Recommendation: drop SYS_ADMIN/SYS_PTRACE, use a tight seccomp profile,
       and avoid mounting the entire repository as /app when not required.

2.2 [MEDIUM] VNC / noVNC exposed without authentication
     - File: docker-compose.yml (verified).
     - Finding: ports 5900 (VNC) and 6080 (noVNC) are published; MODE defaults
       to "gui" (environment: MODE=${MODE:-gui}). If no VNC password is set,
       anyone reaching the ports obtains GUI access to the container.
     - Recommendation: bind to 127.0.0.1, set a VNC password, or place behind
       an authenticated reverse proxy.

2.3 [MEDIUM] Broken build reference — Dockerfile does not exist
     - File: docker-compose.yml references `dockerfile: docker/Dockerfile.v0.8`.
     - Finding: no `docker/Dockerfile.v0.8` exists in the repository (glob for
       "**/Dockerfile*" returns only projetadmin/tests/Dockerfile.proxy — verified).
       As shipped, `docker compose build` will fail and the image
       `modelweaver-v0.8` cannot be built from this repo.
     - Recommendation: commit the referenced Dockerfile (or fix the path),
       and add a CI step that runs `docker compose build` / `docker build`
       to catch missing build context.

3. CODE & IMPLEMENTATION ISSUES   [MEDIUM / LOW]
--------------------------------------------------------------------------------
3.1 [MEDIUM] Broken import in root dsl_executor.py
     - File: dsl_executor.py (root, verified).
     - Finding: `import FSMInterpreter` then `FSMInterpreter.main()`. The
       interpreter is not a top-level module — it lives at
       AgentFrameWork/fsm_interpreter.py. The script raises ModuleNotFoundError
       at runtime (the real entrypoint is AgentFrameWork/__main__.py).
     - Recommendation: fix the import path or remove the dead root script.

3.2 [MEDIUM] SQL identifier interpolation via f-strings
     - File: modules/sql/assign_classes.py (lines 31 and 36, verified).
     - Finding: table/column identifiers are interpolated into SQL using
       f-strings:
         f"SELECT {id_col}, {ref_col} FROM {table} WHERE classe_outil_id IS NULL"
         f"UPDATE {table} SET classe_outil_id=? WHERE {id_col}=?"
       The current call sites use local string literals ("catalogue_outils"/
       "ref"/"outil_id" and "local_outils"/"outil_ref"/"local_outil_id") so they
       are safe today — but the pattern is unsafe if ever fed external input.
     - Recommendation: validate identifiers against a strict allow-list before
       interpolation (never interpolate raw user input into DDL/DML).

3.3 [MEDIUM] Empty / placeholder / stub files at repository root
     - Files (verified by reading each):
         auth.py            : contains only the placeholder text "votre contenu".
         db.py (root)       : stub `Database` class with empty connect()/query()
                              (the real implementation is modules/sql/db.py).
         monitor_simple.py  : dummy `print('hello')`.
         audit_monitoring.py        : only a TODO comment.
         audit_monitoring_panels.py : only a TODO comment.
     - Impact: misleading; a root `db.py` stub can shadow the real module
       depending on sys.path ordering.
     - Recommendation: remove dead root stubs or clearly mark them; keep the
       real implementation under modules/sql/.

3.4 [MEDIUM] Pervasive broad `except Exception:` without logging
     - Finding (verified): the codebase contains 100+ bare `except Exception`
       blocks (grep returned 100+ matches, truncated). Many modules
       (AgentFrameWork/*, AgentsCatalogue/lib/*, services/*, mw-dev-chat/*)
       share the same pattern; numerous handlers swallow silently with `pass`.
       A health/security probe that fails therefore reports a "healthy/missing"
       state rather than surfacing the failure.
     - Recommendation: catch specific exceptions, log (logger.exception) at
       least on health/security-sensitive paths, and distinguish "not present"
       from "check failed".

3.5 [MEDIUM] Dynamic exec() of config / skill YAML (code-execution surface)
     - Files (verified):
         services/depends.py        : exec(compile(iface.read_text(), ...)) of
                                      each unit's _contract/interface.py
                                      (lines 53 and 67).
         services/service_manager.py : _make_handler() exec()s inline "handler"
                                      code from .service.yaml (line 196).
         services/skill_manager.py   : call() exec()s inline `run` code from
                                      *.skill.yaml (line 213).
     - Finding: these execute arbitrary Python sourced from on-disk config /
       skill definitions. The skill path is described as "sandboxed by the host
       agent" (skill_manager.py line 208), but there is no actual sandbox —
       any YAML that an agent is tricked into loading would run with full
       process privileges.
     - Recommendation: restrict these to a vetted, capability-limited
       namespace; treat all skill/contract YAML as untrusted input; consider a
       restricted-eval DSL instead of exec().
